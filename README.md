# Nudge2Green — grocery task, Copenhagen food event

A mock online grocery shop used to collect real shopping baskets from festival
visitors, so they can be compared against baskets generated by LLM personas
conditioned on the same questionnaire answers.

Static site — HTML, CSS and three JS files. No build step, no dependencies,
no backend beyond a Google Apps Script endpoint.

## Participant flow

| # | Screen | What happens |
|---|--------|--------------|
| 1 | Welcome | Language, plain-language info, consent tick |
| 2 | Questionnaire | 10 items, one per screen, auto-advancing |
| 3 | Task brief | *Buy food for three dinners for two people, max 250 DKK* |
| 4 | Shop | 81 products, 8 categories, search, hard budget cap |
| 5 | Done | Participant ID shown as the beer voucher; data is sent |

Danish is the default; the 🇬🇧/🇩🇰 button in the header switches every string,
including product names and package sizes. The choice is remembered on the
device, so a phone used by one participant after another keeps its language.

## Study-design decisions baked into the code

- **No sustainability framing anywhere.** The shop shows price and package size
  only. No CO₂ labels, no green badges, no eco copy — the branding is
  deliberately generic ("Dagligvarer" / "Groceries"). Footprints are joined
  afterwards from `data/co2_factors.csv`, which is **not loaded by the site**,
  so the numbers are not even present in the page a curious participant could
  inspect.
- **The budget is a hard cap.** Anything that would push the basket past
  250 DKK is disabled and labelled *Over budget*, so every basket is comparable
  and the constraint matches the one given to the model.
- **The catalogue order is fixed by default.** Every participant sees the same
  order, which is the control condition for the ordering effect the proposal
  wants to test on the model side. `?shuffle=1` (or `CONFIG.SHUFFLE_CATALOGUE`)
  randomises it, and the order actually shown is recorded in every submission
  along with each item's `position_in_catalogue`.
- **Anonymous by construction.** No name, e-mail, IP logging or cookies. The
  participant ID is a random 5-character code generated in the browser; it is
  both the row key and the beer voucher.

## Files

```
index.html              all five screens, one page
css/style.css           mobile-first, 375px up to desktop
js/config.js            ← paste your Apps Script URL here

js/app.js               survey, shop, basket, payload, submission

data/catalog.csv|.json  catalogue for analysis

data/co2_factors.csv    pack weight + kg CO2e per kg and per pack

```

## Setup

1. Follow [`apps-script/README-SETUP.md`](apps-script/README-SETUP.md) and paste
   the `/exec` URL into `js/config.js`.
2. Host the folder anywhere static — GitHub Pages, Netlify drop, or a laptop on
   the stand's wifi. **HTTPS is required** if you want the QR code to work on
   iPhones without warnings.
3. Generate a QR code pointing at the URL. Useful query parameters:

   | Parameter | Effect |
   |---|---|
   | `?lang=en` | Start in English instead of Danish |
   | `?station=A` | Tag submissions with which device/queue they came from |
   | `?shuffle=1` | Randomise catalogue order for this participant |

   e.g. `https://your-site/?station=ipad2`

Run it locally with:

```bash
python3 -m http.server 8123
```

## Offline resilience

Festival wifi drops. Every submission is written to `localStorage` **before**
the network call and only removed once the server confirms. Queued submissions
are retried on the next page load and whenever the browser comes back online,
and the participant sees a clear message plus a *Try again* button rather than a
silent failure. The Apps Script ignores repeated `participant_id`s, so retries
never duplicate rows.

If a phone is closed while offline, the queue is still in that phone's
localStorage — reopening the site on the same device flushes it.

## After the event

`responses` gives you one row per participant. To compute footprints:

```
basket_items ⋈ data/co2_factors.csv  on product_id
basket_co2e = Σ (qty × co2e_kg_per_pack)
```

`data/catalog_for_prompt.txt` is the same 81 products in a flat
`id | name | size | price | category` form, ready to paste into the persona
prompt so the model chooses from exactly the catalogue the humans saw.

## Adding product photos

Drop `img/<product_id>.jpg` (e.g. `img/m01.jpg`) into `img/` and set
`USE_PHOTOS: true` in `js/config.js`. Any product without a photo falls back to
its emoji tile automatically, so the site works with none, some, or all of them
present. With `USE_PHOTOS` off — the default — no image requests are made at
all and every product shows an emoji tile. Square-ish crops around 400×300 px
look best.

## Changing the catalogue or questionnaire

- **Products:** edit `js/catalog.js`, then re-run the export in
  `data/` (see `data/README.md`) so the analysis files stay in sync.
- **Questions:** edit the `QUESTIONS` array at the top of `js/app.js` and the
  matching strings in `js/i18n.js`. New keys need to be added to
  `RESPONSE_COLUMNS` in `apps-script/Code.gs`, which rewrites the header row on
  the next submission.
